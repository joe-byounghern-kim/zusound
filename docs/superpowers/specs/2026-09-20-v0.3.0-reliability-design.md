## Objective

Prepare a runtime-compatible minor release that makes Zustand integration type-safe, lifecycle behavior predictable, and public documentation and agent Skills useful to consumers. Do not publish to npm, create a release tag, or merge the final v0.3.0 PR as part of preparation.

## Decisions and Alternatives

The approved approach is targeted reliability and developer-experience improvement. A documentation-only refresh would leave integration defects intact. A broad audio-engine redesign would expand regression risk without supporting this release's goals. Keep the existing audio model, defaults, package exports, zero runtime dependencies, and Zustand peer range `>=4.0.0 <6.0.0`.

## Runtime and Type Design

### Zustand middleware composition

Replace the fixed `StateCreator<T, [], []>` public middleware overload with a generic signature that preserves input and output mutator tuples. Register a namespaced Zustand store mutator that adds the existing `zusoundCleanup` API to the resulting store type. Preserve the callable middleware/subscriber interface, base/per-call options, vanilla and React store creation, and existing exported types.

The resulting store must expose `zusoundCleanup()` without casts. Test supported composition with `devtools`, `persist`, and `subscribeWithSelector`, documenting ordering requirements rather than claiming arbitrary middleware combinations. Validate both compile-time inference and runtime behavior. Do not add a runtime Zustand dependency.

### Lifecycle contract

Keep per-store middleware ownership separate from subscriber-instance ownership. Middleware teardown uses the store's `zusoundCleanup()`. Subscriber teardown requires both the returned `unsubscribe()` and the instance's `cleanup()`. The instance cleanup does not promise to detach middleware-created stores. Cleanup is idempotent, clears pending changes and timers, releases retained audio resources once, and prevents late playback after asynchronous resume.

A cleaned-up subscriber instance is terminal. Recommend a fresh `createZusound()` instance for each attachment, including React effect setup and hot-reload boundaries. Do not silently change the shared exported instance's behavior or add implicit resubscription.

### Debounce buffering

Replace append-only pending arrays with a latest-change-per-path buffer shared by middleware and subscriber orchestration. Retained changes must scale with distinct changed paths, not update count. Preserve the existing debounce contract: trailing-edge emission, the last change descriptor for each path, and ordering by the paths' last occurrence. Debounce is not a net-diff calculation or a maximum playback-rate guarantee.

No-op changes do not needlessly retain audio payloads. Teardown empties buffers and cancels timers. Tests cover repeated updates, multiple paths, ordering, timer resets, cleanup before flush, and parity between integration modes. Do not change synthesis or scheduler timing as unrelated refactoring.

### Non-fatal error reporting

Introduce one internal error-reporting boundary used by state-change processing, playback rejection, and audio resume. Preserve `onError(error, context)` and the existing stage union. Exceptions thrown by the diagnostic callback must not escape store updates, trigger recursive reporting, leak resources, or become unhandled playback rejections. Preserve the original failure context and best-effort diagnostic logging. Tests must exercise a throwing callback at each supported reporting boundary.

## Documentation Design

Use the package README as the canonical API and recipe source, preserving the established synchronization markers for root README sections. The root README should prioritize purpose, supported environments, installation, one typed quick start, and navigation. Replace subjective debugging promises with precise descriptions of audible state-change cues.

Cover:

- Development/production defaults and unknown-environment behavior.
- Browser autoplay restrictions, SSR-safe imports, and a repeatable first-signal check.
- Middleware versus subscriber integration and exact cleanup ownership.
- Tested middleware composition and fully typed examples.
- Top-level change paths, immutable-update expectations, equality limitations, and debounce semantics.
- Option defaults, units, ranges, mapping precedence, and non-fatal error behavior.
- Accessibility and user control: audio is optional feedback, not a replacement for visual diagnostics.
- Upgrade notes from v0.2.x, preserving the public API and existing defaults.

Keep the demo API section consistent with the documentation. Do not redesign the demo. Validate public examples through TypeScript fixtures rather than relying solely on Markdown link checks.

## Skills Design

Retain all four canonical skills: onboarding, debugging, migration, and tuning. Give each a distinct trigger, minimal inputs that can usually be inferred from the consumer repository, ordered procedures, concrete decision branches, stop conditions, and rollback instructions.

Verification in a consumer project means its actual typecheck/tests/build plus a reproducible browser state update and lifecycle check. Repository-only `pnpm skills:validate` and `pnpm skills:bridge` belong in maintainer guidance, not consumer acceptance criteria. Use a fresh configured instance for subscriber examples. Never claim to have heard audio from mocked tests. Explain what requires human listening and what can be checked automatically.

References must be linked, internally consistent, and reflect the supported version contract and new typing. Keep generated `.claude/skills/` output uncommitted.

## Implementation Ruling: TypeScript Metadata

Ruling: use Zustand's standard output mutator typing for `zusoundCleanup`, rather than preserving an explicitly empty output-mutator annotation on a wrapped initializer. Investigation demonstrated that `StateCreator<State, [], []>` conflicts structurally with the added cleanup tuple. Intersections erased inference, and overload ordering either erased cleanup or rejected the legacy annotation. No `any` escape or global augmentation of unenhanced stores is acceptable.

The runtime API, defaults, options, and peer range remain unchanged. TypeScript consumers using an explicit state type should use `create<State>()(...)` or `createStore<State>()(...)`, and infer `const enhanced = zusound(initializer)` rather than annotating the wrapped result with an empty output-mutator tuple. Original initializer parameter annotations remain supported. Document this source-level migration in README, Skills, Changeset, and PR. Negative fixtures must reject erased output metadata and cleanup on unenhanced stores. Cost if wrong: consumers need unnecessary type-only edits, so verify the standard form against all three supported matrix versions before delivery.
